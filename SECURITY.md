# Security Policy

`keydris-reader` exists to take credentials out of MCP servers, so a defect here can put a secret
back in. Reports are taken seriously and handled privately.

---

## Reporting a vulnerability

**Do not open a public issue, and do not post it in Discord.**

Use one of these, in order of preference:

1. **GitHub private vulnerability reporting** — the *Security* tab on
   [keydrisLabs/keydris-reader](https://github.com/keydrisLabs/keydris-reader/security/advisories/new).
   This keeps the report, the discussion, and the eventual advisory in one place.
2. **Email** — [security@keydris.com](mailto:security@keydris.com). Please put `keydris-reader` in
   the subject line.

Include whatever you have:

- The affected package and version (`@keydris/kit-reader` or `keydris-kit-reader`), or a commit SHA
- Which component: the library, the framework adapter, a sample server, or the release workflow
- A JSON-RPC body, gateway response, or minimal reproduction, if the issue is on the wire
- What an attacker gains, and what they need in order to get it

Please redact real credentials from anything you send. A prefix and a length are enough.

### What to expect

| Stage | Target |
| --- | --- |
| Acknowledgement | 3 business days |
| Initial assessment, with a severity and a plan | 10 business days |
| Fix released for a confirmed high or critical issue | 30 days, sooner where practical |
| Public advisory | With the fix, or coordinated with you |

We will keep you updated while a fix is in progress, credit you in the advisory unless you would
rather stay anonymous, and let you know if we conclude a report is not a vulnerability, with the
reasoning. We do not currently run a paid bounty.

### Coordinated disclosure

Please give us 90 days before disclosing publicly, or less if we ship a fix sooner. If a report
turns out to affect the Keydris control plane rather than these libraries, we will route it
internally and tell you that we have.

Both libraries are pre-1.0 and version independently. Fixes land on the latest minor of each; there
are no long-term support branches yet.

| Package | Version | Supported |

| `keydris-kit-reader` | 0.1.x | Yes |

## Scope

### In scope

- The two libraries in [`node/packages/kit-reader`](node/packages/kit-reader) and
  [`python/packages/kit-reader`](python/packages/kit-reader)
- The optional adapters: `@keydris/kit-reader/express` and `keydris_kit_reader.mcp`
- The released artifacts on [npm](https://www.npmjs.com/package/@keydris/kit-reader) and
  [PyPI](https://pypi.org/project/keydris-kit-reader/), and the workflows that publish them
- The sample servers, where a defect would mislead someone copying from them

Findings we especially want to hear about:

- A path where a released credential is written to a log, a traceback, an error message, or a
  `repr`
- A body shape that redeems a token for an action other than the one it authorizes, or that gets
  two actions out of one token
- A way to make the reader send a live token anywhere other than the configured gateway
- A credential surviving past the call it was released for, through the adapters or the samples
- A refusal that leaks token or credential material into the `problem` string an agent receives
- Supply-chain issues in the release pipeline: tag/manifest mismatch, provenance, dependency
  confusion on either package name

### Out of scope

- The Keydris control plane — proxy, gateway, and vault. Those are not in this repository; report
  them through [keydris.com](https://keydris.com/) or the email above.
- Vulnerabilities in GitHub, npm, PyPI, or the MCP SDKs themselves. Report those upstream; tell us
  if this repository needs a mitigation.
- Anything reachable only by an integrator ignoring a documented rule below — for example logging
  `credentials` deliberately. We would still like to know if the documentation is what misled you.
- What a server does with a credential *after* redemption. See the next section.
- Reports generated by a scanner with no demonstrated impact.

## The threat model

### What the libraries defend against

- **A secret at rest in the MCP server.** There is nothing to steal between requests. An attacker
  needs to be present during an authorized call.
- **A token that outlives its action.** The tool name and exact arguments travel with the token, so
  the gateway evaluates policy against the call that is really about to happen. A body carrying two
  tokenized `tools/call`s is refused before the gateway is touched.
- **Ambiguous authorization.** If a request carries both a `_meta` token and a header token and they
  disagree, redemption refuses rather than picking one — choosing either would let one transport
  override the other's authorization.
- **Credentials spent on discovery.** `initialize` and `tools/list` never reach the gateway, so no
  secret is released for a request that does not need one.
- **A token sent somewhere it cannot be spent.** The Python reader rejects a non-`http(s)`
  `gateway_url` at construction, because `urlopen` would otherwise honour `file:` or `ftp:`. Node's
  `fetch` refuses those schemes itself.
- **A gateway that misbehaves.** Non-JSON error pages, empty credential arrays, and unreachable
  hosts all degrade to a readable refusal rather than a crash or a hang. The Python default
  transport carries a mandatory 10-second deadline.
- **A secret in a traceback.** `Released.__repr__` is redacted in Python.

### What they cannot defend against

These are the integrator's responsibility, and no library-side change can enforce them:

1. **Serve stateless, build per request.** A long-lived MCP session outlives the short-lived
   (~5 minute) token that authorized it. Keep the released credential on the stack of the call it
   was released for, and **never cache a `Redemption`.** Node builds a fresh server and transport
   with `sessionIdGenerator: undefined`; Python uses `stateless_http=True` and the middleware drops
   the ContextVar in a `finally`.
2. **Never log `credentials`.** The `problem` side is safe to log freely; it carries no secret.
   Python redacts `Released` reprs — **Node does not**, so `console.log(redemption)` there prints
   the secret.
3. **Node has no redemption timeout.** A hung gateway hangs the tool call for as long as `fetch`
   allows. Pass an instrumented `fetch` with an `AbortSignal` if that matters to you.
4. **Applying a credential overwrites.** A released header replaces any header of the same name you
   set beforehand, and a released query parameter replaces one of the same name in the URL. That is
   intentional — the vault's routing decides the final value — but your defaults lose.
5. **Raw batches are yours to police.** A body with one tokenized and one untokenized `tools/call`
   yields a redemption bound to the tokenized call; a handler closing over a single redemption would
   let both see it. JSON-RPC batching was dropped in MCP 2025-06-18 and the proxy mints per action,
   so this is not reachable through the intended path — but if you accept raw batches on your own
   transport, reject them or scope the redemption per message. The Python MCP adapter is
   structurally immune: it runs post-dispatch and never sees a batch.
6. **Host and port are security configuration, not just deployment.** The proxy's `dst_addr` becomes
   the token's `dst`, and the gateway looks the credential up by that host — so moving off
   `localhost` means moving the proxy scope, the registered MCP connection URL, and the vault
   routing entry together.

### Deliberately out of scope

The library governs **which MCP server receives a credential**, not what that server then does with
it. The sample's subsequent `GET https://api.github.com/user` is trusted server behavior. Governing
that downstream call would mean routing the server's egress through Keydris too.

## Hardening checklist for deployers

- Point `gatewayUrl` / `gateway_url` at an **HTTPS** endpoint in anything but local development.
- Serve stateless, and build the MCP server per request.
- Log the `problem`, never the `Redemption`. Keep `credentials` out of structured logging, error
  reporters, and tracing payloads.
- Give the redemption call a deadline: the Python default transport already has one, Node needs an
  instrumented `fetch`.
- Scope the vault entry as narrowly as the routing allows — host pattern, path pattern, and exactly
  one matching entry, so the gateway never has to guess.
- Keep the *integration* rule (may this action run) and the *credential* rule (may this secret be
  released to this origin) as two separate decisions. The gateway evaluates both before consuming
  the token.
- Set `KEYDRIS_ALLOWED_HOSTS` on the Python sample when serving anything other than localhost.
- Pin the library version and verify provenance. Both packages publish with trusted publishing via
  GitHub OIDC — npm provenance and a PEP 740 attestation on every release.
- Do not put a fallback credential in the environment "just in case". It defeats the point, and it
  will be the thing that leaks.
